## Goal

Add all remaining Wacky Manor characters as full LLM + Eidos autonomous agents.
Upgrade existing characters to use new Eidos structured personality features.
Expand the mansion with 3 new rooms.

**Verdict gate:** All 17 characters have validated personalities. Key interactions
(Muttley medal exchange, Blubber Bear map retrieval) work through LLM reasoning
guided by structured goals — no scripting needed.

---

## Design Principles

1. **No character is special.** All characters are autonomous LLM + Eidos agents.
   There is no NPC tier system, no scripted-vs-autonomous distinction in the engine.
2. **Game mechanics hierarchy:** Goals + state first. Soft constraints second.
   Hard constraints third. Scripting only as last resort when nothing else works.
3. **Personality drives behavior.** A character's Jungian function stack, goals,
   and constraints determine how they act. The engine treats every character
   identically — `CharacterAgentLoop` runs for all.

## 1. Descriptor Templates

### 1.1 Genre Template: `hanna-barbera-cartoon-style`

Shared by all 17 characters. Located at `META-INF/eidos/resources/hanna-barbera-cartoon-style.yaml`.

Covers four conventions:
- **Expository soliloquy** — narrate your situation aloud
- **Emotional telegraphing** — state emotions explicitly and with exaggeration
- **Situation recap** — restate significant events aloud
- **Catchphrase repetition** — use signature phrases regularly

### 1.2 Role Templates (parameterized)

| Template | Parameters | Applied to |
|---|---|---|
| `cartoon-villain` | catchphrase, nemesis, scheme_style | Hooded Claw, Dastardly |
| `cartoon-hero` | love_interest, heroic_style | Peter Perfect |
| `cartoon-protector` | charge, protection_style | Ant Hill Mob |

Additional role templates created as characters need them. Not every character
needs a role template — the genre template plus briefing is sufficient for
characters with unique archetypes (Pat Pending, Slag Brothers, etc.).

### 1.3 Descriptor Composition Order

For each character, the system prompt renders in order:
1. Genre template (hanna-barbera-cartoon-style)
2. Role template with substituted parameters (if applicable)
3. Briefing (character-specific personality details only)
4. Disposition axes and weighted profile
5. Goals (from first-class `AgentGoal` fields)
6. Constraints (from first-class `AgentConstraint` fields)

Briefings become significantly shorter — genre conventions and goals are
handled structurally, not repeated in prose.

## 2. Structured Goals and Constraints

### 2.1 Goals

Goals move from briefing prose to first-class `AgentGoal` fields with priority
and visibility. The `ObservationBuilder` already renders a `== Your Goals ==`
section — this continues to work, now reading from structured fields.

Example (Hooded Claw):
```yaml
goals:
  - name: eliminate-penelope
    description: Kill Penelope Pitstop before she finds the treasure
    priority: PRIMARY
    visibility: PRIVATE
  - name: maintain-cover
    description: Appear helpful and trustworthy as Sylvester Sneekly
    priority: PRIMARY
    visibility: PRIVATE
  - name: win-treasure
    description: Win the treasure hunt
    priority: SECONDARY
    visibility: PUBLIC
```

Example (Muttley):
```yaml
goals:
  - name: collect-medals
    description: Collect medals — real, fake, any medals. You love medals.
    priority: PRIMARY
    visibility: PUBLIC
  - name: follow-dastardly
    description: Follow Dastardly around. He sometimes gives you medals.
    priority: SECONDARY
    visibility: PUBLIC
```

### 2.2 Constraints

Behavioral guardrails using `AgentConstraint` with severity:

```yaml
constraints:
  - name: maintain-disguise
    description: Never reveal your true identity as the Hooded Claw when others are present
    severity: HARD
  - name: elaborate-schemes
    description: Your schemes should be elaborate and theatrical
    severity: SOFT
```

Constraints are added per-character only when goals alone cannot produce
the required behavior. Most characters start with zero constraints. If
testing reveals a character breaking a game mechanic, a targeted constraint
is added and retested.

## 6. Engine Changes

### 6.1 No Engine Changes Required

The engine treats all characters identically:
- `ScenarioOrchestrator.runScenario()` iterates `world.characters()` and
  creates a `CharacterAgentLoop` for each. Adding characters is purely
  data — new entries in `characters.yaml` and `descriptors.yaml`.
- `ActionResolver` handles all action types for all characters.
- `ObservationBuilder` renders per-character observations for all characters.

### 6.2 Scaling Consideration

17 simultaneous LLM agents is significantly more than 5. Each character
makes an LLM call per turn with a think delay between turns.

Mitigations:
- Characters in empty rooms with no stimuli will WAIT more often (fewer
  meaningful LLM calls)
- Think delays already vary per character — slower characters (Lazy Luke)
  call less frequently
- The `max-turns` config caps total actions

If performance is unacceptable, reduce concurrent agents by having some
characters start inactive and activate when a player character enters
their room. But this is an optimization — defer until needed.

## 7. What Doesn't Change

- **CharacterState** — no tier field, no type field. Same model for all.
- **CharacterAgentLoop** — same loop for all characters.
- **ActionResolver** — same action vocabulary for all characters.
- **SceneDirector** — preserved for scripted sequences if ever needed.
- **TriggerEvaluator** — preserved. Existing triggers still work.
- **WebSocket protocol** — `snapshot`, `position`, `dialogue` events unchanged.
  More characters means more events, but the protocol handles this.
- **Qhorus channels** — same 3-channel structure. New room topics auto-created.
