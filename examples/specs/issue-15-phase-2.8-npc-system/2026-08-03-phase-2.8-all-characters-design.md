## Goal

Add all remaining Wacky Manor characters as full LLM + Eidos autonomous agents.
Upgrade existing characters to use new Eidos structured personality features.
Expand the mansion with 3 new rooms.

**Verdict gate:** All 17 characters have validated personalities. Key interactions
(Muttley medal exchange, Blubber Bear map retrieval) work through LLM reasoning
guided by structured goals — no scripting needed.

---

## Design Principles

1. **No character is special.** All characters are autonomous LLM + Eidos agents.
   There is no NPC tier system, no scripted-vs-autonomous distinction in the engine.
2. **Game mechanics hierarchy:** Goals + state first. Soft constraints second.
   Hard constraints third. Scripting only as last resort when nothing else works.
3. **Personality drives behavior.** A character's Jungian function stack, goals,
   and constraints determine how they act. The engine treats every character
   identically — `CharacterAgentLoop` runs for all.

## 1. Descriptor Templates

### 1.1 Genre Template: `hanna-barbera-cartoon-style`

Shared by all 17 characters. Registered via `META-INF/eidos/templates.yaml`
(Eidos #99 DescriptorTemplate + TemplateRef with `${variable}` substitution).

Covers four conventions:
- **Expository soliloquy** — narrate your situation aloud
- **Emotional telegraphing** — state emotions explicitly and with exaggeration
- **Situation recap** — restate significant events aloud
- **Catchphrase repetition** — use signature phrases regularly

### 1.2 Role Templates (parameterized)

| Template | Parameters | Applied to |
|---|---|---|
| `cartoon-villain` | catchphrase, nemesis, scheme_style | Hooded Claw, Dastardly |
| `cartoon-hero` | love_interest, heroic_style | Peter Perfect |
| `cartoon-protector` | charge, protection_style | Ant Hill Mob |

Additional role templates created as characters need them. Not every character
needs a role template — the genre template plus briefing is sufficient for
characters with unique archetypes (Pat Pending, Slag Brothers, etc.).

### 1.3 Descriptor Composition Order

For each character, the system prompt renders in order:
1. Genre template (hanna-barbera-cartoon-style)
2. Role template with substituted parameters (if applicable)
3. Briefing (character-specific personality details only)
4. Disposition axes and weighted profile
5. Goals (from first-class `AgentGoal` fields)
6. Constraints (from first-class `AgentConstraint` fields)

Briefings become significantly shorter — genre conventions and goals are
handled structurally, not repeated in prose.

## 2. Structured Goals and Constraints

### 2.1 Goals

Goals move from briefing prose to first-class `AgentGoal` fields (Eidos #100)
with priority and visibility. The `ObservationBuilder` already renders a
`== Your Goals ==` section — this continues to work, now reading from
structured fields.

The game engine can query goals programmatically via `AgentQuery.byGoal()`
and `AgentDescriptor.hasGoal()` / `hasConstraint()` (Eidos #101). This
enables goal-driven termination checks, cooperative/competitive reasoning,
and future mechanics that inspect character motivations.

Example (Hooded Claw):
```yaml
goals:
  - name: eliminate-penelope
    description: Kill Penelope Pitstop before she finds the treasure
    priority: PRIMARY
    visibility: PRIVATE
  - name: maintain-cover
    description: Appear helpful and trustworthy as Sylvester Sneekly
    priority: PRIMARY
    visibility: PRIVATE
  - name: win-treasure
    description: Win the treasure hunt
    priority: SECONDARY
    visibility: PUBLIC
```

Example (Muttley):
```yaml
goals:
  - name: collect-medals
    description: Collect medals — real, fake, any medals. You love medals.
    priority: PRIMARY
    visibility: PUBLIC
  - name: follow-dastardly
    description: Follow Dastardly around. He sometimes gives you medals.
    priority: SECONDARY
    visibility: PUBLIC
```

### 2.2 Constraints

Behavioral guardrails using `AgentConstraint` with `ConstraintSeverity`
(Eidos #103). The renderer discriminates: MARKDOWN uses `[HARD]`/`[SOFT]`
labels, PROSE groups by severity, A2A_CARD carries the field for machine
routing.

```yaml
constraints:
  - name: maintain-disguise
    description: Never reveal your true identity as the Hooded Claw when others are present
    severity: HARD
  - name: elaborate-schemes
    description: Your schemes should be elaborate and theatrical
    severity: SOFT
```

Constraints are added per-character only when goals alone cannot produce
the required behavior. Most characters start with zero constraints. If
testing reveals a character breaking a game mechanic, a targeted constraint
is added and retested.

## 6. Engine Changes

### 6.1 Minimal Engine Changes

The engine treats all characters identically — `ScenarioOrchestrator`
iterates `world.characters()` and creates a `CharacterAgentLoop` for each.
Adding characters is primarily data (YAML). However, scaling from 5 to 17
agents surfaces issues that need addressing:

**Thread safety (review finding):**
- `CharacterState.inventory` (`ArrayList`) is accessed from character
  threads and the game loop thread. Switch to `CopyOnWriteArrayList` or
  synchronize access.
- `WorldState` event log and taken-objects set need synchronized access
  under 17 concurrent writers.

**max-turns scaling (review finding):**
- Current `max-turns=60` is per-action globally. With 17 characters,
  that's ~3.5 actions each — too few for meaningful interactions.
  Scale to `max-turns=300` (17-18 actions per character).

**Think delay defaults:**
- `CharacterAgentLoop.thinkDelay()` currently has explicit cases for
  `lazy-luke` and `sergeant-blast` only. Add a configurable default
  per character in `characters.yaml` rather than hardcoding agent IDs.

**Startup validation:**
- Validate at scenario start that every character in `characters.yaml`
  has a matching Eidos descriptor. Fail fast with a clear error rather
  than NPE at runtime.

### 6.2 Scaling Consideration

17 simultaneous LLM agents is significantly more than 5. Mitigations:
- Characters in rooms with no stimuli WAIT more often (fewer LLM calls)
- Think delays vary per character — slower characters call less frequently
- Entrance-hall overcrowding (7 characters start there) creates an initial
  burst — consider spreading starting positions across rooms

If performance is unacceptable, activate characters on-demand when a
player character enters their room. Defer until needed.

## 8. Test Plan

### 8.1 Unit Tests

- **DescriptorTemplateTest** — genre template renders in system prompt,
  role template substitutes parameters, composition order is correct
- **GoalRenderingTest** — structured goals appear in `== Your Goals ==`
  observation section, visibility filtering works (PRIVATE goals only
  shown to owning character)
- **ConstraintRenderingTest** — constraints appear in system prompt with
  severity-appropriate language (HARD: "You MUST...", SOFT: "You should...")
- **WeightedProfileTest** — disposition weights render in system prompt,
  dominant-auxiliary hierarchy expressed correctly

### 8.2 Integration Tests

- **AllCharactersStartTest** — 17 characters load from YAML, all get
  CharacterAgentLoop instances, scenario starts without errors
- **RoomExpansionTest** — 6 rooms load, adjacency works, characters
  can move between all connected rooms

### 8.3 LLM Evaluation (llm-eval profile)

Uses the built-in Eidos eval judges (no custom evaluation infrastructure):
- **MbtiAlignmentJudge** — MBTI-70 questionnaire alignment for MBTI-typed characters
- **FunctionActivationJudge** — TAA (Target Activation Accuracy) per cognitive function
- **PersonalityEvolutionJudge** — PSA (Personality Stability Accuracy) across turns

For each new character:
- **Voice test** — produces recognizable voice in first response
- **Soliloquy test** — uses expository soliloquy convention
- **Goal-driven behavior test** — acts on structured goals without
  being told what to do
- **MBTI alignment** — MbtiAlignmentJudge validates personality profile
  (MBTI-typed characters only)
- **Function activation** — FunctionActivationJudge validates dominant/auxiliary
  function usage in scenario responses

Key interaction tests:
- **Muttley medal exchange** — GIVE fake-medal, Muttley gives brass-key
- **Blubber Bear map retrieval** — gentle approach vs startling
- **Slag Brothers riddle** — asking about the riddle triggers smashing
- **Blast/Meekly dynamic** — Blast blocks, Meekly helps when Blast absent

### 8.4 DispositionHealth (Eidos #116)

- `DispositionHealth.probe()` returns `Aligned` / `Drifted` / `EvolutionPending`
- Each character's responses align with declared Jungian function stack
- Weighted profiles produce measurable personality alignment scores
- Regression: existing 5 characters maintain or improve alignment after
  structured Eidos upgrade
