# Design: Auto-Generate Zod Schemas from TypeScript Interfaces

**Issue:** casehubio/casehub-pages#411
**Date:** 2026-09-06
**Branch:** issue-411-auto-generate-zod-schemas

## Overview

Three deliverables that eliminate dynamic property passthrough end-to-end:

1. **Interface audit** — complete all TypeScript interfaces so every YAML property maps to a declared field
2. **Schema generator** — a ts-morph script that reads interfaces and emits Zod schemas, replacing the hand-written `component-schemas.ts`
3. **Desugarer validation** — replace the passthrough loop with `schema.parse()` so only declared properties survive

Principle: all TypeScript must be type-safe. All YAML properties must map to typed properties — no dynamic passthrough.

## 1. Interface Audit

### The problem

`displayer-desugar.ts` lines 374-385 pass through any YAML key not in its `handledKeys` set:

```typescript
for (const [key, value] of Object.entries(raw)) {
    if (!handledKeys.has(key) && !(key in props)) {
        props[key] = value;  // dynamic passthrough
    }
}
```

Properties like `text`, `value`, `csvExport`, `selection`, `selectionKey`, `refresh`, `visible`, `title`, `width`, `height` work at runtime via this passthrough but may not be declared in their component's TypeScript interface.

### Audit approach

For each of the 55 component types in `ComponentTypeRegistry`:

1. Read the TypeScript interface and list its declared properties
2. Check sample YAML files in `examples/samples/` for properties used on that component type
3. Check the desugarer code paths for properties extracted explicitly (these should already be in interfaces)
4. Any property that works in YAML but isn't in the interface → add to interface

Known gaps from #408 investigation:
- `MetricProps` — missing `text`, `value` (used in every metric sample)

### Properties from `DataComponentCommon` vs desugarer sections

Several `DataComponentCommon` properties can be set two ways in YAML:
- **Modern format** (flat in `properties:`): `title: Revenue` — passes through the passthrough loop
- **Legacy format** (nested in `general:`): `general: { title: Revenue }` — explicitly extracted by desugarer

Both paths must work. The interface already declares these (`title`, `visible` are in `DataComponentCommon`). The desugarer's explicit extraction from `general:` is a YAML convenience, not a type gap. These are NOT audit findings.

### Deliverable

Updated TypeScript interfaces in `pages-component/src/model/displayer-types.ts` and related files. All interfaces must be complete — the schema generator and desugarer validation depend on this.

## 2. Schema Generator

### Script: `packages/pages-schema/scripts/generate-schemas.ts`

A ts-morph script that:

1. Creates a `ts-morph` Project pointing at `packages/pages-component/tsconfig.json`
2. Finds `ComponentTypeRegistry` in `type-guards.ts`
3. For each registry entry (e.g., `"bar-chart": BarChartProps`):
   a. Resolves the full type including inherited properties from `extends`
   b. Walks every property, mapping TypeScript types to Zod schemas
   c. Filters out function-typed properties (`cellSpan`, `renderAfterHeader`, `mergeRows` callback form)
   d. Emits a named export: `export const barChartPropsSchema = z.object({...})`
4. Writes `packages/pages-schema/src/component-schemas.generated.ts`

### Type mapping rules

| TypeScript | Zod |
|-----------|-----|
| `string` | `z.string()` |
| `number` | `z.number()` |
| `boolean` | `z.boolean()` |
| `"a" \| "b" \| "c"` (string literal union) | `z.enum(["a", "b", "c"])` |
| `SomeInterface` (object type) | `z.object({...})` (recursive) |
| `readonly T[]` / `T[]` | `z.array(...)` |
| `Record<string, T>` | `z.record(z.string(), ...)` |
| `T \| undefined` / optional property | `.optional()` |
| `DataSetLookup` (branded/opaque) | `lookupSchema` (import from pages-data) |
| `ColumnId` (branded string) | `z.string()` |
| `DataSetId` (branded string) | `z.string()` |
| `FieldSchema` (recursive) | `fieldSchemaZod` (hand-written, referenced) |
| Function types | **filtered out** (not representable in YAML) |

### Special cases

- **`DataComponentCommon`** and **`ChartSettings`** — extracted as shared base schemas. The generator detects `extends` and emits `.merge()` or `.extend()` calls.
- **`lookupSchema`** — the lookup field uses the existing `lookupSchema` from `pages-data` (it has transforms for YAML normalization). The generator emits an import reference, not an inline schema.
- **`FieldSchema`** — recursive JSON Schema type. Hand-written `fieldSchemaZod` using `z.lazy()`. The generator references it rather than attempting recursive generation.
- **Branded types** (`ColumnId`, `DataSetId`) — treated as plain strings for Zod purposes. The branding is a TypeScript-only concern.

### Generated file header

```typescript
// AUTO-GENERATED by scripts/generate-schemas.ts — DO NOT EDIT
// Re-generate: yarn workspace @casehubio/pages-schema run generate
// Source: packages/pages-component/src/model/
```

### CI staleness check

A test in `pages-schema` runs the generator in dry-run mode and compares the output to the committed file. If they differ, the test fails:

```
FAIL: component-schemas.generated.ts is stale.
      Run 'yarn workspace @casehubio/pages-schema run generate' to update.
```

### Package script

```json
{
  "scripts": {
    "generate": "tsx scripts/generate-schemas.ts",
    "build": "yarn generate && tsc -p tsconfig.build.json"
  }
}
```

### Dependencies

Add to `pages-schema` devDependencies:
- `ts-morph` — TypeScript compiler wrapper for reading interfaces
- `tsx` — for running the generator script

## 3. Desugarer Validation

### `displayer-desugar.ts` changes

Replace the passthrough loop with schema validation:

```typescript
import { componentSchemaRegistry } from "@casehubio/pages-schema";

// ... existing extraction logic ...

// REPLACE passthrough loop (old lines 374-385) with:
const schema = componentSchemaRegistry.get(type);
if (schema) {
  const validated = schema.safeParse(props);
  if (validated.success) {
    return { type, props: validated.data, ...(visibleWhen ? { visibleWhen } : {}) };
  }
  // On validation failure: use props as-is but log warning
  // (graceful degradation during migration)
  console.warn(`Schema validation failed for ${type}:`, validated.error.issues);
}

return { type, ...(Object.keys(props).length > 0 ? { props } : {}), ...(visibleWhen ? { visibleWhen } : {}) };
```

### `component-desugar.ts` changes

For types that pass `properties` verbatim (schema-form, legend, form inputs, action-button, submit-button), add schema validation:

```typescript
// Before: props: raw["schema-form"] as Record<string, unknown>
// After:
const rawProps = raw["schema-form"] as Record<string, unknown>;
const schema = componentSchemaRegistry.get("schema-form");
const props = schema ? schema.parse(rawProps) : rawProps;
```

### Graceful degradation

During the migration period, use `safeParse` (not `parse`) to avoid breaking existing YAML that uses undeclared properties. Log warnings so interface gaps are discoverable. Once the interface audit is complete and all warnings are resolved, switch to strict `parse` that rejects unknown properties.

### Dependency addition

Add `@casehubio/pages-schema` as a dependency of `@casehubio/pages-ui` (where the desugarers live).

## Testing Strategy

### Interface audit tests
- For each component type, a test verifies every property used in `examples/samples/` YAML is declared in the interface
- Type-compatibility tests (existing from #408) verify schema output matches interface

### Generator tests
- Staleness test: generated file matches committed file
- Round-trip test: generator output parses valid test data without error
- Function-filter test: properties with function types are excluded

### Desugarer tests
- Existing desugarer tests continue to pass (no behavioral change for valid YAML)
- New tests: undeclared properties are stripped (not passed through)
- New tests: validation warnings are emitted for unknown properties in graceful mode

## Execution Order

1. **Interface audit first** — schemas can't be correct until interfaces are complete
2. **Generator second** — produces schemas from the fixed interfaces
3. **Desugarer third** — uses the generated schemas to validate

Each batch is independently testable and committable.
