# Design: ts-morph Generation Pipeline for Domain Zod Schemas

**Issue:** casehubio/casehub-pages#420
**Date:** 2026-09-11
**Branch:** issue-420-lsp-schemas

## Overview

Replace the hand-written Zod schemas in `lsp-schemas` (blocks-ui) for the
four domain YAML formats — CaseDefinition, SWF, HTN, Org — with schemas
generated by a ts-morph pipeline. The generator reads TypeScript interfaces
from graph-stencil-* packages and `@openworkflowspec/sdk`, strips index
signatures, recovers key-presence unions via declarative manifests, and emits
one `.generated.ts` file per format. A vitest staleness test makes upstream
type drift a CI failure.

## 1. Generator Script

**Location:** `lsp-schemas/scripts/generate-domain-schemas.ts` in blocks-ui

Modeled on the component schema generator in `pages-schema/scripts/generate-schemas.ts`
(casehub-pages), with three key differences:

### 1.1 Entry points per format

Each domain format has its own root type and source package:

| Format | Root type | Source package | Source file |
|--------|-----------|----------------|-------------|
| CaseDefinition | `CaseHub` | `graph-stencil-case` | `src/types/generated/case-definition.ts` |
| SWF | workflow root | `@openworkflowspec/sdk` | `.d.ts` from node_modules |
| HTN | decomposition root | `graph-stencil-htn` | `src/types/` |
| Org | organization root | hand-written | (to be located in graph-stencil-* or lsp-schemas) |

The generator iterates over a format manifest that declares the root type
name and source file for each format.

### 1.2 Strip index signatures

During the property walk, skip any property whose declaration is an
`IndexSignatureDeclaration` in ts-morph. The CaseDefinition generated
types have `[k: string]: unknown | undefined` on most sub-objects (e.g.
`CaseSignals` items, `Binding`, `Worker`). Stripping these produces tight
Zod schemas with only declared properties — essential for accurate LSP
completion and diagnostics.

Implementation: when calling `type.getProperties()`, filter out properties
where `prop.getValueDeclaration()?.getKind() === SyntaxKind.IndexSignature`
or where the property name is a computed index key.

### 1.3 Split tsconfig

Per GE-20260907-d0ccd0, use a separate `tsconfig.generator.json` with
`paths` mapping workspace packages to source directories:

```json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "paths": {
      "@casehubio/graph-stencil-case": ["../graph-stencil-case/src/index.ts"],
      "@casehubio/graph-stencil-htn": ["../graph-stencil-htn/src/index.ts"],
      "@casehubio/graph-stencil-swf": ["../graph-stencil-swf/src/index.ts"]
    }
  }
}
```

This avoids the stale-dist gotcha (GE-20260907-156200) where ts-morph
resolves workspace package types via `dist/` and sees 0 properties for
correctly-named types.

The build tsconfig (`tsconfig.json` / `tsconfig.build.json`) does NOT
include these paths — they would break `rootDir` constraints.

### 1.4 Output

One `.generated.ts` file per domain format, replacing the current
hand-written schemas:

- `src/schemas/case-definition.generated.ts`
- `src/schemas/swf.generated.ts`
- `src/schemas/htn.generated.ts`
- `src/schemas/org.generated.ts`

Each generated file has a header:

```typescript
// AUTO-GENERATED by scripts/generate-domain-schemas.ts — DO NOT EDIT
// Re-generate: yarn workspace @casehubio/lsp-schemas run generate
// Source: <source-package>/<source-file>
import { z } from "zod";
```

## 2. Discriminator Manifests

### 2.1 Directory structure

```
lsp-schemas/
  discriminators/
    case-definition.json
  scripts/
    generate-domain-schemas.ts
```

### 2.2 Manifest format

Each manifest declares paths where key-presence unions occur:

```json
{
  "spec.bindings[]": {
    "strategy": "key-presence",
    "variants": {
      "subCase": ["name", "subCase"],
      "humanTask": ["name", "humanTask"],
      "trigger": ["name", "trigger"]
    }
  }
}
```

- **Path:** Dot-separated with `[]` for array items. Identifies where in
  the type tree to apply union recovery.
- **Strategy:** `key-presence` — the variant is determined by which
  optional keys are present.
- **Variants:** Map of variant name to the list of properties that belong
  to that variant. Shared properties (like `name`, `guard`) appear in
  every variant's list.

### 2.3 Generator integration

When the generator reaches a declared path during the type walk, instead
of emitting one `z.object()` with all properties optional, it emits:

```typescript
z.union([
  z.object({ name: z.string(), subCase: subCaseRefSchema }),
  z.object({ name: z.string(), humanTask: humanTaskRefSchema }),
  z.object({ name: z.string(), trigger: triggerSchema, guard: z.string().optional() }),
])
```

### 2.4 Format registration wiring

The format registrations in `lsp-schemas/src/formats/` already support
`variantDispatchers` via the `FormatRegistration` type from `pages-lsp`.
The generated variant schemas feed into these dispatchers:

```typescript
variantDispatchers: new Map([
  ['spec.bindings[]', {
    strategy: 'key-presence',
    variants: new Map([
      ['subCase', subCaseBindingSchema],
      ['humanTask', humanTaskBindingSchema],
      ['trigger', triggerBindingSchema],
    ]),
  }],
]),
```

This gives the LSP context-appropriate completion — suggesting `subCase`
properties when the `subCase` key is present, not `humanTask` properties.

### 2.5 Scope

HTN, SWF, and Org are structurally simpler — they likely don't need
manifests initially. The directory grows as needed.

## 3. Type Mapping Rules

The generator reuses the core type-to-Zod mapping from the component
generator, with domain-specific additions:

| TypeScript | Zod | Notes |
|-----------|-----|-------|
| `string`, `number`, `boolean` | `z.string()`, `z.number()`, `z.boolean()` | Same as component generator |
| String literal unions | `z.enum([...])` | Same |
| `T[]` / `readonly T[]` | `z.array(...)` | Same |
| `Record<string, T>` | `z.record(...)` | Same |
| Optional / `T \| undefined` | `.optional()` | Same |
| `[k: string]: unknown` | **skipped** | Index signature stripping (D2) |
| Function types | **skipped** | Not representable in YAML |
| Recursive types | `z.lazy()` | HTN task/method, CaseDefinition GoalExpression |
| `unknown` | `z.unknown()` | Intentionally open-ended fields (SWF input/output/use) |

### 3.1 Recursive type detection

HTN has mutual recursion between `htnTaskSchema` and `htnMethodSchema`.
CaseDefinition has self-referencing `GoalExpression`. The generator
detects cycles during the type walk by tracking visited type symbols in
a `Set<string>`. When a cycle is detected, the generator emits a
`z.lazy()` wrapper at the cycle-breaking point:

```typescript
const htnMethodSchema: z.ZodType<unknown> = z.lazy(() => z.object({
  guard: z.string().optional(),
  tasks: z.array(htnTaskSchema),
}));
```

### 3.2 Shared type deduplication

When the same sub-type appears in multiple positions (e.g.
`mcpTransportSchema` used by `workerFunctionSchema`), the generator
emits it once as a named const and references it by name. This keeps
the generated output readable and avoids code bloat.

## 4. Staleness Tests

### 4.1 Test file

`lsp-schemas/test/staleness.test.ts`:

1. Creates a ts-morph Project using `tsconfig.generator.json`
2. Runs the same generation logic the script uses, capturing output
   strings in memory (no filesystem writes)
3. Reads the committed `.generated.ts` files from disk
4. Asserts string equality per format

Failure message:

```
FAIL: schemas/case-definition.generated.ts is stale.
      Run 'yarn workspace @casehubio/lsp-schemas run generate' to update.
```

### 4.2 CI integration

The staleness test runs as part of `yarn test` in CI. When upstream types
change (e.g. a field added to `CaseHub` in graph-stencil-case), the test
fails, forcing the developer to regenerate.

## 5. Format Registration Updates

The existing format registrations in `lsp-schemas/src/formats/` stay
mostly unchanged — `contentDetector`, `symbolExtractor`, and `extensions`
are preserved. Two changes per format:

1. **Schema import** switches from hand-written to generated:
   ```typescript
   // Before
   import { caseDefinitionDocumentSchema } from '../schemas/case-definition.js';
   // After
   import { caseDefinitionDocumentSchema } from '../schemas/case-definition.generated.js';
   ```

2. **Variant dispatchers** are wired for formats with discriminator
   manifests (CaseDefinition initially).

## 6. Dependencies

Add to `lsp-schemas` devDependencies:
- `ts-morph` — TypeScript compiler wrapper for reading domain interfaces
- `tsx` — for running the generator script

No new runtime dependencies — generated files import only from `zod`.

## 7. Package Scripts

```json
{
  "scripts": {
    "generate": "tsx scripts/generate-domain-schemas.ts",
    "build": "yarn generate && tsc -p tsconfig.build.json",
    "test": "vitest run"
  }
}
```

## 8. Execution Order

1. **Generator script** — the core ts-morph pipeline with index signature
   stripping, recursive type detection, and discriminator manifest reading
2. **Discriminator manifests** — JSON files declaring key-presence unions
   for CaseDefinition (and others as needed)
3. **Generated schemas** — run the generator to produce `.generated.ts`
   files, verify they match or improve on the hand-written schemas
4. **Format registration updates** — switch imports, wire variant dispatchers
5. **Staleness test** — vitest test comparing committed vs fresh generation
6. **Existing test suite** — all existing lsp-schemas tests must pass with
   generated schemas

Each step is independently committable and testable.
